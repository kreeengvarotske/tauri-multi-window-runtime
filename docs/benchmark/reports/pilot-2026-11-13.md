# Scenario M pilot, 13 November 2026

**Pilot: descriptive, no conclusion.** All 72 scheduled runs completed and
all 72 were valid under the frozen analysis. This report concerns one native
Windows machine and the recorded environment only. It makes no inferential
saving, equivalence, non-inferiority, or general product-performance claim.
It does not freeze thresholds, approve confirmatory work, or authorize a run.

The observed C-minus-A paired RAM differences were positive in all three
two-window cells, including D16 and D64. At four windows with D64, the
observed RAM and CPU differences were negative. The CPU difference was
positive at N2D0 and negative in the three cells containing data. Those
directions, including the unfavorable small-cell RAM results, are retained
below without selecting a favorable subset.

## Validity and measurement quality

Every cell and arm has six valid runs out of six. Every comparison has six
valid within-triplet pairs per cell. There were no invalid, failed,
timed-out, replaced, or rerun positions in this completed pilot. All 72 app
and monitor exit codes were zero. Every report existed and passed; every
profile was newly created. Every job recorded zero leftover processes,
`jobTerminated: false`, and no job error.

The RAM outcome is `LoadPrivateMBAvg`: the time average of summed Private
Bytes over the host and observed WebView2 process tree during load.
Despite the legacy `MB` field names, the monitor divides by PowerShell
`1MB` (2^20 bytes), so this report labels memory **MiB**. Working Set is
diagnostic only and is not used for a saving statement.

The CPU outcome is `RunCpuSeconds`: Job Object user plus kernel CPU for the
whole tree from process start through the end of idle-after, using the last
eligible job row at or before that boundary. All 72 CPU sources were `job`.
Startup and load CPU remain secondary measures; their monitor-derived
counterparts are retained as diagnostics alongside the job values.

|---|---:|

| Median load sample interval | 1.0065–1.016 s |
| Largest load sample gap | 1.061–2.509 s |

The validity checks accepted the sampling and membership records. Job CPU
includes short-lived members that the monitor missed. RAM remains sampled:
a process that begins and ends between monitor samples can be absent from
the Private Bytes observations. The approximately one-second memory
sampling cannot establish a true instantaneous peak. Process-level load
Private Bytes, including host and each observed WebView2 identity, remain
in archived `analysis/processes.csv` and the raw diagnostics.

## Retained data, memory split, and model limits

Generator representation sizes were approximately 16.0 and 64.0 MiB for
D16 and D64. The renderer JS-heap diagnostics, summed across windows, rose
with the per-window copies in A: medians were 34.8 MiB at N2D16, 132.7 at
N2D64, and 265.5 at N4D64. In B and C those summed medians were
approximately 2.2, 2.2, and 4.4/4.3 MiB respectively. JS heap does not
account for the whole WebView2 Private Bytes measurement.

| Cell | Arm | Host load Private MiB | WebView2 load Private MiB |
|---|---|---:|---:|
| N2D0 | A / B / C | 6.1 / 6.0 / 5.9 | 239.1 / 249.8 / 248.1 |
| N2D16 | A / B / C | 8.5 / 27.5 / 28.2 | 302.1 / 356.7 / 356.4 |
| N2D64 | A / B / C | 9.1 / 85.1 / 85.8 | 426.0 / 356.2 / 357.5 |
| N4D64 | A / B / C | 13.4 / 86.2 / 87.1 | 710.1 / 587.3 / 588.2 |

Thus a smaller renderer JS heap did not imply a smaller total at N2D16 or
N2D64. At N2D64, C−A paired medians were +76.6 MiB host and −68.7 MiB
WebView2. At N4D64 they were +73.4 MiB host and −123.9 MiB WebView2.
Those paired component medians need not sum exactly to the paired total
median. This localizes the observations but does not establish their cause.

At N2, C's median host Private increment above D0 was 22.3 MiB at D16 and
80.0 MiB at D64, approximately 39% and 25% above the nominal Rust sizes.
B's increments were 21.5 and 79.1 MiB. These retained host measurements
include costs beyond the generator representation. Their deviation exceeds
the 20% condition in protocol §4 and must be addressed in the review of
data sizes or window counts before a confirmatory freeze, with the reason
for the resulting choice recorded. This report approves no such change.

Protocol §5 proposes `Saving(N) = N*S − K`, where
`S = Dw + Ww − Tw` and `K = Δrt + Dr + Wr + I`. A descriptive D64 fit
uses N2D64 and N4D64 within the same triplet block:
`S = (Saving(4) − Saving(2))/2`, `K = 2*S − Saving(2)`, with
`Saving = A − comparison arm`. The six blockwise fits give these combined
terms; ranges are observed spread:

| Arm versus A | Outcome | S per window, median [min, max] | K, median [min, max] |
|---|---|---:|---:|
| B | RAM MiB | 31.8 [25.9, 44.0] | 70.4 [58.5, 92.3] |
| C | RAM MiB | 32.9 [23.8, 44.2] | 78.0 [54.3, 96.9] |
| B | CPU s | 5.17 [3.46, 6.61] | 1.80 [−3.17, 5.94] |
| C | CPU s | 5.39 [3.51, 7.07] | 2.62 [−2.61, 7.09] |

Two observed window counts determine a line exactly and do not validate
linearity. The matrix cannot separately identify every component of S and
K, and lacks N4D0. The N2D0 C−A difference (+7.1 MiB, +2.22 s) is a
fixed-overhead diagnostic at two windows, not a separately identified
`Δrt`. At N2, the RAM behavior from D0 through D16 to D64 is not a single
demonstrated linear data-size response. No unmeasured break-even cell is
claimed. Among measured cells, N4D64 is the only cell whose C−A RAM and CPU
differences were both below zero throughout the observed pair ranges.
The smallest measured data cell with all C−A CPU differences below zero
was N2D16. These are descriptive locations in this matrix, not thresholds
or population conclusions.

Each arm appeared twice in each position per cell. The archived position
table further splits comparisons by the first arm, with only two pairs per
stratum. C−A RAM stratum medians stayed positive in all N2 cells and
negative in N4D64; CPU stratum medians kept the corresponding directions
above. Magnitudes varied, so this small pilot cannot rule out order effects.

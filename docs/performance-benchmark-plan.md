# План измерения производительности Runtime Framework

## Цель

Проверять не предположение, а измеримый эффект оптимизаций runtime: память, CPU, задержку, число фактических вычислений и поведение при нескольких окнах.

Сравнение должно отвечать на два разных вопроса:

1. Что даёт наш runtime по сравнению с тем же приложением на обычном Tauri?
2. Как оба варианта соотносятся с сопоставимым приложением на Electron?

Tauri и Electron используют разные архитектуры, поэтому результат относится к конкретному сценарию и тестовой конфигурации. Нельзя обобщать результат одного теста на все приложения.

## Обязательные варианты

- **Tauri baseline** — минимальное приложение на Tauri без нашего runtime.
- **Tauri + runtime** — то же пользовательское поведение с runtime-core/runtime-ipc.
- **Electron baseline** — минимальный аналогичный сценарий на Electron.

Все три варианта должны показывать одинаковый экран и выполнять эквивалентную работу. Зафиксировать версии runtime, Tauri, WebView2/Electron, Node/Rust, ОС, архитектуру CPU и объём RAM.

## Сценарии тестирования

1. **Простой:** приложение открыто, данные не запрашиваются.
2. **Одна операция:** запрос метаданных одного проекта.
3. **Параллельные одинаковые запросы:** N запросов одного ключа одновременно.
4. **Несколько окон:** 1, 2 и 4 окна, одинаковая нагрузка из каждого.
5. **Много разных ключей:** кэширование большого числа независимых результатов.
6. **Инвалидация одного ключа:** сброс одного проекта во время работы с другими.
7. **Очистка всего кэша:** очистка при наличии активных операций.
8. **Длительная нагрузка:** повторяющийся сценарий в течение 5–10 минут, чтобы заметить рост памяти.
9. **Закрытие окон:** закрытие вторичного окна и завершение приложения; проверить, что задачи и ресурсы корректно освобождаются.

Каждый сценарий запускать минимум 5 раз после отдельного прогрева. Публиковать медиану и диапазон, а не только лучший результат. Для сравнений использовать одинаковые входные данные и одинаковое число запросов.

## Метрики

- **Память:** private/working set каждого процесса и суммарно по всему дереву процессов приложения; отдельно записывать пик и значение после прогрева.
- **CPU:** среднее потребление и пики за одинаковый интервал.
- **Задержка:** p50 и p95 времени ответа, время холодного старта и время до готовности UI.
- **Работа runtime:** количество входящих запросов, реальных выполнений, объединённых запросов, cache hits и ошибок.
- **Устойчивость:** ошибки, зависшие задачи и рост памяти в длительном сценарии.

Не складывать одинаковые показатели разных типов и не сравнивать только главный процесс: renderer/WebView/GPU/utility-процессы тоже входят в стоимость приложения.

## Контроль условий

- Одна машина и одна версия ОС на время сравнительной серии.
- Закрыть лишние приложения; не запускать сборку проекта во время замеров.
- Одинаковые разрешение окна, контент, частота запросов и продолжительность сценария.
- Отдельно помечать холодный старт и прогретый запуск.
- Не смешивать debug и release-сборки. Основное сравнение проводить на release, debug можно измерять отдельно.
- Сохранять сырые результаты CSV/JSON, команды запуска и версию коммита.
- Не считать симулированную задержку доказательством ускорения CPU или памяти: измерять фактическую работу и ресурсы процессов.

## Формат результата

Для каждого запуска сохранять:

- дату и идентификатор коммита;
- вариант приложения и сценарий;
- параметры нагрузки и количество окон;
- сырые замеры по времени;
- суммарные показатели дерева процессов;
- число запросов/выполнений/cache hits;
- примечания о сбоях и отклонениях.

Итоговая таблица должна содержать baseline, вариант с runtime, абсолютную разницу и процентную разницу. Если разница меньше разброса измерений, фиксировать результат как неубедительный, а не как улучшение.

## Критерии готовности первого этапа

- [ ] Описаны одинаковые сценарии для трёх вариантов.
- [ ] Есть воспроизводимая процедура запуска и сбора данных.
- [ ] Сохраняются сырые данные, а не только итоговая цифра.
- [ ] Сделано не менее пяти повторов на сценарий.
- [ ] Память учитывается по всему дереву процессов.
- [ ] Не заявляется преимущество без результатов сравнения.

## Границы первого этапа

Сначала измеряем текущую реализацию и строим baseline. Не добавляем оптимизации только ради улучшения цифр. После первых результатов выбираем узкое место и проверяем гипотезу отдельным изменением, сохраняя одинаковые тесты до и после.
